# QQ 刷新性能实测

2026-11-12，本机 Apple M3 Max、16 核、64 GiB 内存、接通电源。测量当前 ChatLab QQ 适配器，主消息库 1,006,633,984 字节，约 120 万条历史消息。

结论：本机内存占用较低，刷新时主要使用一个 CPU 核心；需要控制的是持续变化时每轮约 2 GiB 的系统记账写入，以及后台稳定快照失败造成的等待和重试。现有证据不支持直接改为每 30 秒；采集服务每 5 分钟检查是较保守的取值。

## 当前路径

原始读取器曾每次重建全量规范化索引；当前接入版已经改成：复制及哈希三个核心库 → 认证解密 → 扫描全部原生 ID → 只解析新增消息 → 独立存档。仍存在全量复制、解密和 ID 扫描，但不再每轮解析百万条历史。

## 两轮真实前台刷新

| 指标                 |        第 1 轮 |        第 2 轮 |
| -------------------- | -------------: | -------------: |
| 新增消息             |              7 |              1 |
| 总耗时               |       10.91 秒 |        7.85 秒 |
| CPU 消耗             | 约 7.87 CPU 秒 | 约 7.07 CPU 秒 |
| 平均占用单核         |         约 72% |         约 90% |
| 按 16 核折算全机算力 |        约 4.5% |        约 5.6% |
| 系统记账磁盘读取     |        995 MiB |         85 MiB |
| 系统记账磁盘写入     |      2,085 MiB |      2,085 MiB |

两轮测试在同一进程执行，进程峰值 RSS 约 175 MiB；采样到的峰值 physical footprint 约 143 MiB。两种内存口径不同，不能相加。原有后台服务空闲 20 秒观察：CPU 约 0、RSS 约 84 MiB、磁盘读取 0。

| 阶段                         | 第 1 轮耗时 | 第 2 轮耗时 |
| ---------------------------- | ----------: | ----------: |
| 复制、哈希与稳定性检查       |     0.67 秒 |     0.64 秒 |
| 主消息库解密和检查           |     3.74 秒 |     3.70 秒 |
| 联系人与群信息解密           |     0.29 秒 |     0.27 秒 |
| 全量 ID 比对、提取新行       |     1.46 秒 |     1.18 秒 |
| 新消息及联系人等元数据索引   |     2.01 秒 |     1.96 秒 |
| 追加消息、重算受影响会话统计 |     2.74 秒 |     0.07 秒 |

第二轮仅影响极少量数据且缓存更热，因此入库统计及读取显著降低；不能从两个样本推断所有群或任意消息数量下的耗时。接入版仍会重建联系人等元数据索引，此阶段每轮约写入 99 MiB；复制与解密输出合计贡献约 1.94 GiB 写入。

连续 10 次源文件未变化检查均返回 `unchanged`，每次约 0.6～1.0 毫秒，无磁盘读取。20 次本地接口检查中，health 中位数约 3.0 毫秒，会话列表中位数约 7.7 毫秒；此项没有覆盖刷新提交期间的最坏响应时间。

## 后台情况与失败样本

已有后台服务的 6 次成功日志耗时为 232.53、60.98、41.41、69.25、50.84、75.82 秒。232.53 秒发生在初次大批量导入期间；其余 5 次中位数为 60.98 秒。这是历史成功样本，不是稳定延迟保证，也没有测得 P95。

额外用相同 `ProcessType=Background` 启动一次测量任务，首轮耗时 111.26 秒、CPU 约 5.71 秒，在稳定副本检查阶段耗尽 3 次重试，返回 `source_busy`。系统记账写入约 3,026 MiB，未进入解密和索引。采样时主线程在文件 `open` 中等待；这只能证明当时存在文件 I/O 等待，不能据此确定后台与前台差异的全部原因。

测量器随后一次立即检查也因 `source_busy` 失败，耗时 7.11 秒、写入约 3,026 MiB；因此没有获得后台无变化检查样本。所有失败都未提交新消息，原有成功存档仍可用。

由此可见，失败的复制重试也有成本，短轮询间隔不能保证短延迟。单纯增加 CPU 或内存不能直接解决稳定捕获失败。

## 刷新频率判断

如果 QQ 每轮都变化，按前台两轮平均值粗算，且像当前实现一样在刷新结束后再等待：

| 等待间隔 | 单核平均占用 |  系统记账写入量 |
| -------- | -----------: | --------------: |
| 30 秒    |       约 19% | 约 186 GiB/小时 |
| 5 分钟   |      约 2.4% |  约 24 GiB/小时 |

这是持续有变化、全部刷新成功且耗时等同本次前台样本的计算场景，不是实测长期流量。无变化时会跳过大规模读写，失败重试则可能增加读写；后台耗时较长也会改变每小时执行次数。系统记账写入不等于 SSD NAND 实际写入或寿命损耗。

结束时复核实际配置：QQ 采集服务每轮结束后等待 300 秒，ChatLab 自动导入当前为 20 分钟，区别于此前接入记录中的 5 分钟；本次测量没有调整两者。ChatLab 拉取间隔变长并不会降低独立采集服务的整库复制频率。

后续若要缩短延迟，优先减少整库副本和解密输出、避免反复重建元数据索引，以及改进稳定副本捕获；需各自验证 QQ WAL 和认证一致性，不能仅按文件大小或最新消息时间跳过数据。

## 方法与可复核产物

- 对实际 `QQSource.refresh()` 的复制、解密、ID 比对、索引及入库调用逐段计时；两轮正常追加共 8 条真实新消息，沿用现有去重，不改刷新间隔或消息格式。
- CPU、内存及 I/O 使用 macOS `proc_pid_rusage`；CPU tick 使用 `mach_timebase_info` 转换，并用 `getrusage` 的 0.3 秒计算循环核对。CPU 秒是计算时间，wall 秒包含等待。
- 未清空系统缓存，未制造磁盘压力，未测试电池续航或能耗，也未将前台结果视为后台服务的延迟承诺。
- 临时后台测量任务已卸载，原有 QQ 服务继续运行。
- 测量脚本、逐阶段 JSON、后台样本与接口统计保存在仓库外的 `~/.local/share/chatlab-qq/performance/`，不含密钥和聊天正文。报告只保留汇总统计。
